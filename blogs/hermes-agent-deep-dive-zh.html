Hermes Agent 架构深度解析

从真实源码与文档出发，拆解一个个人 AI Agent 如何把"多平台消息"和"一次对话循环"彻底解耦——以及它怎么自己进化、记住你。

DL
By Daniel Liu · August 23, 2026 · 12 min read

Hermes 的核心分层：Agent 只管一次对话，复杂度全在 Gateway 与各平台适配器。

这是一篇基于 Hermes Agent 真实源码与 docs 的技术解析（仓库 hermes-agent），不是泛泛而谈的产品介绍。我会拆四个能力：Message Gateway（多平台消息网关）、WhatsApp 接入适配、Self-Improving（技能策展 / 自我进化）、Long-Term Memory（长期记忆如何落地）。每个能力都给：架构、核心方法分析、以及我在源码里扒出来的真实坐标（file:line）。

0. 全景：Agent Core 与 Gateway 的分层

先建立心智模型。Hermes 的核心是一个 AIAgent 类（run_agent.py），它只负责"一次对话循环"。所有"从哪个聊天软件来、回哪个聊天软件去"的复杂度，都被推到 GatewayRunner（gateway/run.py，约 31k 行）和各平台 BasePlatformAdapter 子类里。

关键设计原则（来自 AGENTS.md）：Per-conversation prompt caching is sacred——每轮对话复用缓存前缀，任何中途改动 system prompt 或 tool schema 都会让缓存失效、成本翻倍。所以 Gateway 必须在"复用同一份 agent 实例"和"多会话隔离"之间精打细算。

1. Message Gateway（多平台消息网关）

入口契约是 BasePlatformAdapter.handle_message(event)（gateway/platforms/base.py:6045）。每个平台适配器（Telegram、Discord、Slack、WhatsApp、Signal…）都继承它。适配器把平台原始消息归一化成 MessageEvent，交给 GatewayRunner 的 _handle_message（gateway/run.py:16462）。

GatewayRunner 内部再分两层：会话路由层（按 session_key 找/建会话、活跃会话锁、工具审批流）和 TurnRunner（gateway/run.py:5348，真正跑一轮 agent 循环、流式输出、把 tool 结果喂回去）。这套切分让"平台协议复杂度"和"agent 核心逻辑"互不污染。

设计直觉：Gateway 不是 agent 的"前端"，而是 agent 的"邮局"——它只负责把信（MessageEvent）正确投递、把回信（final_response）正确发出，绝不替 agent 思考。

2. WhatsApp 接入

WhatsApp 走 Meta 的 Cloud API：webhook 收消息 → Graph API 发消息。WhatsAppCloudAdapter.connect()（gateway/platforms/whatsapp_cloud.py:435）注册 webhook 校验与消息回调。三个工程细节值得记：

  • 抗重试：Meta 的 webhook 会重复投递，靠 _dedup_wamid 去重，避免一条消息触发两次回复。
  • 抗错误扩散：dispatch 失败时只 log 不抛——一条消息发不出去，不该炸掉整个 webhook 处理循环。
  • 谁该被回复：mixin 里的 mention / allowlist 策略决定"群聊里只有 @ 我才回"，避免成骚扰机器人。
"Self-Improving 不是让 agent 改自己的代码，而是把经验固化为 skill。"

3. Self-Improving（自我进化）

这里最容易误读。Hermes 的"自我进化"不是让模型在线改源码，而是把可复用的经验固化为 skill（SKILL.md 形式的流程知识），由后台 Curator 做管家。

agent/curator.py 的 run_curator_review（:1511）是一个纯函数状态机：扫描现有 skill、判断是否需要合并/归档/更新，可选调用 LLM 做"语义合并"。关键工程取舍：

  1. 默认零 LLM 成本——状态机本身不调模型，只有真正需要语义判断时才花 token。
  2. dry-run 可预演——先打印"将要做什么"，确认无误再落地。
  3. pinned skill 永不动——被显式钉住的 skill 跳过所有自动化，防止策展把人工精心写的内容冲掉。

4. Long-Term Memory（长期记忆）

记忆分两条线。一条是事实记忆：MemoryManager → MemoryProvider（后台线程、串行、去噪），最朴素的一版 MemoryStore（tools/memory_tool.py:159）直接落 MEMORY.md 到磁盘（save_to_disk() @ :387）。另一条是会话记忆：hermes_state.py 用 FTS5 建全文索引（含 CJK tokenizer messages_fts_cjk，:2685），这就是 session_search 能跨会话检索的底座。

5. 小结 Takeaways

  • Gateway 的本质：把"平台协议复杂度"和"agent 核心循环"彻底解耦，整套设计围绕"prompt caching 不可破坏"这条铁律。
  • WhatsApp：Cloud API + webhook + Graph API；抗重试靠 _dedup_wamid，抗错误扩散靠"dispatch 失败只 log 不抛"。
  • Self-Improving：经验→skill，Curator 用"纯函数状态机 + 可选 LLM 合并"做后台管家，默认零成本、可预演、pinned 不动。
  • Long-Term Memory：事实走 MemoryManager → Provider，会话走 SessionDB + FTS5；最朴素的 MemoryStore 直接落盘并在 drift 检测上修过竞态。
