post-cortex: Self-Hosted Semantic Memory for Hermes

How the post-cortex plugin and daemon give Hermes structured, shared, semantic long-term memory — without replacing built-in MEMORY.md or the gateway story.

DL
By Daniel Liu · October 18, 2026 · 12 min read

Part 5 of the architecture series covers an optional community memory provider. Built-in tracks — MEMORY.md facts and SessionDB FTS5 — are in Part 4. post-cortex adds a Hermes plugin plus a self-hosted daemon for typed records in an entity graph with local semantic search (RocksDB or SurrealDB, local embeddings), without replacing the gateway story in earlier parts.

Why a separate stack?

Built-in Hermes memory is deliberately simple: facts in markdown files, sessions in SQLite FTS5. That fits most deployments. post-cortex targets teams that want structured knowledge (decisions, fixed problems, code changes, requirements, definitions), semantic recall before each turn, and shared workspaces across profiles or other clients — with everything stored locally. The plugin registered in hermes-agent plugin-catalog; sources live at hermes-plugin-post-cortex and post-cortex (Rust daemon).

Architecture: plugin, daemon, workspace

You install two pieces: catalog plugin hermes-plugin-post-cortex and a separately hosted post-cortex daemon with the pcx CLI. The plugin is a Hermes memory provider — not a personal skill bundle; the only bundled skill is post-cortex:memory for record-format hints.

Each Hermes profile talks to one HTTP daemon (default http://127.0.0.1:3737). The plugin maps the profile name to a workspace via glob rules in post-cortex.json, and opens a per-profile session (default hermes:{profile}). Records carry typed entities and relations; the daemon embeds text with a local model (Model2Vec by default) and runs hybrid retrieval. Nothing leaves your machines except optional remote daemon URLs you configure.

Turn-time recall

When auto_recall is on, the plugin searches the profile's workspace before each turn. Weak hits, bare entity stubs, and noise matching skip_patterns are dropped. Up to max_items (default 5) records above min_score (default 0.62) are injected, truncated by item_chars. If the daemon is slow or down, recall is skipped after timeout_s — the turn still runs.

Tools and skill

  • post_cortex_search — semantic search over records (and optionally captured messages).
  • post_cortex_record — write a typed record into the graph.
  • post_cortex_context — neighbourhood and reverse dependencies for named components.
  • skill_view("post-cortex:memory") — record format and search tips (post-cortex:memory skill).

The provider wires recall, mirroring, and the tools above; it does not ship a general skill pack beyond post-cortex:memory. Daemon 0.5+ adds cards (user + project notes in the system prompt), authorship (hermes:{profile} on records), and opt-in capture of completed turns into a message stream (primary agent only; cron and subagents never auto-write).

Mirroring built-in memory

With mirror_memory_writes: true, what the primary agent saves through Hermes's built-in memory tool is also stored as a post-cortex record. Cron jobs and subagent runs do not get automatic mirroring — only the main agent path.

Multi-profile workspaces

workspaces maps profile-name globs to a shared workspace name — first match wins. Example: {"ops-*": "Ops", "dev-*": "MyProject", "*": "hermes"} lets ops profiles share one graph while defaults stay isolated. Other post-cortex clients (e.g. a coding agent on the same project) can read the same workspace.

Install and versions

Requires Hermes ≥ 0.22.2 and a daemon ≥ 0.4.0 (cards, authorship, and capture need 0.5.0).

Daemon. Install the Rust CLI with cargo install post-cortex-daemon --features "embeddings,surrealdb-storage" or brew install julymetodiev/tap/post-cortex. Run pcx start — default base URL http://127.0.0.1:3737. Daemon options live in ~/.post-cortex/daemon.toml; for non-loopback binds set PC_AUTH_TOKEN (or auth_token in the file) and list client hosts in allowed_hosts / PC_ALLOWED_HOSTS.

Plugin. hermes plugins install post-cortex, then hermes memory setup and choose post-cortex, or set memory.provider: post-cortex in the profile config.yaml. Start a new session; hermes memory status confirms the daemon is reachable.

Secrets and config

Connection. URL: url in $HERMES_HOME/post-cortex.json, else env PCX_URL (default loopback). Token: PCX_TOKEN through Hermes secret scope — never written into that JSON. When auth is on, match PCX_TOKEN to the daemon's auth_token / PC_AUTH_TOKEN.

Recall thresholds, workspaces, capture, and the rest of the plugin knobs also live in post-cortex.json. Remote daemons need aligned token and allowed_hosts, and usually a private network or TLS in front of the plugin's plain HTTP client.

Desktop. Hermes Desktop has no separate post-cortex protocol: pick post-cortex as the memory provider in the GUI and enter the same URL and token. The daemon must still be running — typically pcx start on your machine before you chat.

Cloud / shared host. Run pcx as its own service (VM, container, or always-on host), point each profile's PCX_URL at that base URL, and require token plus allowed_hosts so the daemon accepts your clients' Host headers.

Minimal sketch: {"url": "http://127.0.0.1:3737", "workspaces": {"*": "hermes"}, "auto_recall": true, "mirror_memory_writes": true} — see the plugin README for the full key list.

Takeaways

  • Optional provider: complements MEMORY.md / FTS5; switch via memory.provider, not a gateway rewrite.
  • Typed + semantic: entity graph and local embeddings on your daemon; recall injects a small, scored context block each turn.
  • Shared by workspace: glob-map profiles (and other clients) into one long-term store.
  • Primary-agent writes: mirrored memory and optional capture; subagents/cron stay out of the auto-write path.
