The Message Gateway: Decoupling Platforms from the Agent

The entry contract

Every platform adapter — Telegram, Discord, Slack, WhatsApp, Signal, and the rest — funnels through one method: BasePlatformAdapter.handle_message in gateway/platforms/base.py. Its job is to normalize whatever the platform handed you into a MessageEvent and forward it to GatewayRunner._handle_message. The agent never sees “Telegram update” versus “WhatsApp webhook”; it only sees a typed event stream. The Gateway internals doc maps the surrounding files; this chapter follows one message through the parts that matter for operators and contributors.

The handler returns immediately: adapters spawn the real turn in a background task so inbound webhooks do not block and control commands can still reach the runner while a model turn is in flight.

async def handle_message(self, event: MessageEvent) -> None:
    if not self._message_handler:
        return
    if event.allow_gateway_control:
        coerce_plaintext_gateway_command(event)
    session_key = build_session_key(event.source, ...)
    # ... _process_message_background() -> GatewayRunner._handle_message(...)

Three behaviors worth naming explicitly (not “two details … third …”). Early return when _message_handler is unset lets adapters register before the runner wires up — messages no-op until the handler exists. Gateway commands in plain text are coerced when allow_gateway_control is true, so /stop and friends work even on platforms without native slash commands. Background spawn is what makes the dual-layer busy guard possible: the adapter can queue or interrupt without deadlocking the webhook thread.

Session key

Before authorization or model work, the adapter derives a session_key with build_session_key() in gateway/session.py — the only supported way to name a conversation lane. Never concatenate IDs by hand; multiplexing, threads, and per-user group isolation all live in that function.

Layout (default profile namespace main):

agent:{namespace}:{platform}:{chat_type}[:{scope_id}][:{chat_id}][:{thread_id}][:{participant_id}]

Examples: agent:main:telegram:dm:123456789 for a DM; agent:main:slack:group:C012345:U987654 when group_sessions_per_user isolates speakers in a channel. Slack inserts scope_id (workspace) before chat ids; WhatsApp DMs canonicalize phone identifiers; Discord thread continuity can normalize chat_type to thread so follow-ups byte-match the same key.

Two knobs from config flow into every call:

  • group_sessions_per_user (default on) — in groups, append the sender so each human gets a private agent lane unless you intentionally share one session.
  • thread_sessions_per_user (default off) — forum topics, Discord threads, and Slack threads stay shared across participants unless you opt into per-user thread lanes.

The same triple (platform, chat, scope) always yields the same key. That stability is what lets the gateway cache agents, persist sessions, and attach prompt-cache breakpoints per lane. See Gateway session lifecycle for SessionStore, session_id rotation, and housekeeping that does not change the key.

Authorization

After the key is known, GatewayRunner evaluates whether this sender may talk to the bot. Checks run in order (first match wins toward allow); anything unmatched falls through to deny:

  1. Per-platform allow-all (e.g. TELEGRAM_ALLOW_ALL_USERS)
  2. Per-platform allowlist (e.g. TELEGRAM_ALLOWED_USERS)
  3. DM pairing — an already-authorized user runs /pair, shares the code, the newcomer sends it; state persists in gateway/pairing.py across restarts
  4. Global allow-all (GATEWAY_ALLOW_ALL_USERS / gateway.allow_all_users in config)
  5. Default: reject with no agent turn

Pairing is the escape hatch for DMs on platforms where you cannot pre-seed an employee ID list: the bot stays closed by default, but trusted users can onboard one person at a time without editing env files. For production group bots you typically combine allowlists with mention gating (platform-specific), not pairing.

TurnRunner owns the agent core: load history for this session_key, run tool approval if needed, stream one conversation loop, return final_response. Protocol adapters never import agent tools; the runner never parses Telegram JSON. That split is what keeps twenty platforms from forking the agent.

Design intuition: the Gateway is not the agent’s “frontend” — it is the agent’s post office. It delivers the letter (MessageEvent) and sends the reply; it does not think for the agent.

Dual-layer guard, interrupt, and queue

When a turn is already running, Hermes uses two sequential guards (documented as “Two-Level Message Guard” in gateway internals):

Level 1 (gateway/platforms/base.py): if the session is active, the message lands in _pending_messages and an interrupt event wakes the in-flight turn. Level 2 (gateway/run_inbound.py + run_busy.py): _running_agents tracks the live AIAgent. Bypass commands must reach the runner synchronously — they are dispatched with await self._message_handler(event) instead of another background task, avoiding races with tool approval.

busy_input_mode (gateway config) decides what a non-command message does while busy:

  • interrupt (common default) — call interrupt() on the running agent so the new user text becomes the next steering input; pending text can be dropped on gateway restart.
  • queue — append to a FIFO per session (/queue items plus overflow in session state); survives restart when drain-on-shutdown is enabled.
  • steer — like interrupt but routes through running_agent.steer(), including fan-out to active subagents where delegation would make a blunt interrupt unsafe.

Operators feel this as: send a long task, paste a correction — interrupt mode pivots the turn; queue mode lets you stack messages and inspect depth with /queue; /stop always hard-stops regardless of mode. Compression locks and active subagents can demote interrupt to queue automatically so you do not orphan a parent-session rotation mid-compaction.

Delivery ledger

Generating a reply is not the same as the user receiving it. gateway/delivery_ledger.py records a durable delivery obligation in state.db around each final outbound send (see Messaging):

  • record_obligation() — pending before the first platform send
  • mark_attempting() — immediately before the await
  • mark_delivered() / mark_failed() — only after a definitive SendResult

Semantics are at-least-once. If the gateway dies after the model finishes but before WhatsApp acknowledges, the next boot’s sweep_recoverable() claims rows whose owner process is gone and redelivers the stored text instead of re-running the whole turn (and paying for inference again). A live-process retry sweep handles transient failed rows with backoff (30s / 2m / 10m). Recovery responses may carry a prefix warning when the wire outcome was ambiguous — the ledger would rather surface a possible duplicate than silently lose an answer. Ephemeral slash replies and empty bodies skip the ledger; opt out with gateway.delivery_ledger: false if you accept crash loss.

Circuit breaker

Each platform adapter sits behind a circuit breaker. Repeated retryable failures — disconnects, rate limits, upstream 5xx — trip the breaker: the adapter pauses, logs a structured trip event, and can notify the home channel. Unlike the delivery ledger (which retries obligations), the breaker does not auto-heal; you clear it with /platform resume <platform> once the provider is healthy again. That prevents a sustained outage from reconnect thrash. Use /platform list and gateway logs (circuit breaker, paused) to see what tripped.

Prompt cache and why the Gateway owns the session boundary

Anthropic-style prompt caching attaches cache_control markers to a stable prefix plus the rolling tail of the transcript (agent/prompt_caching.py). The default layout is system-and-3: up to four breakpoints — static system prefix, end of system prompt, and the last three cacheable non-system messages — unless a configured static_system_prefix splits the system block further. Details and hygiene thresholds live in Context compression and caching.

Why the Gateway must own session_key:

  • Agent LRU cache (gateway/run_agent_cache.py) maps session_key → AIAgent. Reusing the same instance keeps the in-memory tool registry and config signature stable; eviction commits memory but does not rotate the durable transcript id.
  • Cache invalidation is global per agent instance — changing system prompt sections, tool schemas, or model route mid-lane forces a rebuild and cold cache writes. The gateway reloads history from the DB each turn but avoids rebuilding agents unless config drift demands it.
  • Platform-blind agent — Telegram and Slack share one lane if they share a key (they should not); each lane gets its own cached agent and its own cache breakpoints. Multiplexed profiles namespace keys (agent:work:…) so parallel configs do not poison each other’s prefixes.

Gateway session hygiene (rough 85% pre-turn compaction) and in-agent compression (≈50% default) are separate layers, but both assume the Gateway already decided which conversation file to open. Prompt caching is the economic reason the agent stays a pure “one loop per turn” object while the Gateway handles everything about which loop.

Takeaways

  • One event contract — adapters normalize to MessageEvent; build_session_key() names the lane.
  • Closed by default — allowlists and DM pairing; deny unless a layer explicitly allows.
  • Busy is policy — dual-layer guard plus busy_input_mode; /stop and /queue are first-class.
  • Replies survive crashes — delivery ledger redelivers finals; circuit breaker pauses sick adapters.
  • Cache follows the session boundary — per-session_key agent cache and system-and-3 markers; do not fork keys by hand.

Primary references: Gateway internals, Session lifecycle, Messaging, Context compression and caching.

WhatsApp Integration: Cloud API, Webhooks, and Failure Isolation

The Cloud API shape

WhatsApp uses a webhook to receive messages and the Graph API to send them. WhatsAppCloudAdapter.connect() (gateway/platforms/whatsapp_cloud.py:435) registers the webhook verification handshake and the inbound message callback. Once verified, every user message arrives as a webhook POST, gets normalized into a MessageEvent, and flows into the GatewayRunner we covered in part 1. For real, the method first refuses to start if deps or config are missing, then builds the two transports — an inbound webhook server and an outbound httpx client:

async def connect(self, *, is_reconnect: bool = False) -> bool:
    if not check_whatsapp_cloud_requirements():
        self._set_fatal_error("whatsapp_cloud_deps_missing", ...)
        return False
    if not self._phone_number_id or not self._access_token:
        self._set_fatal_error("whatsapp_cloud_unconfigured", ...)
        return False
    # Outbound HTTP client with tight keepalive.
    self._http_client = httpx.AsyncClient(
        timeout=30.0, limits=platform_httpx_limits())
    # Inbound webhook server next ...

Note the two fail-closed guards up front: a missing dependency or an unconfigured phone number id / token stops the adapter before it can half-start. That discipline is what keeps a misconfigured bot from silently eating webhooks.

Retry-resistance

Meta's webhook redelivers — a message can arrive two or three times. The adapter guards with _dedup_wamid, keyed on the platform's message id, so one message never triggers two replies. Without it, every flaky delivery would double your agent's answer (and its cost).

Failure containment

When dispatch to a recipient fails, the handler only logs — it does not throw. One undeliverable message must not crash the entire webhook-processing loop, or every other conversation on that adapter goes dark. Containment at the edge keeps one bad send from cascading.

Who actually gets a reply

In a group, you don't want the bot answering every line. A mention / allowlist policy in the adapter mixin decides "only reply when @-mentioned," so it stays a helper instead of a spam bot. This is the same pattern every chatty adapter needs; WhatsApp just makes it visible because groups are noisy.

Takeaways

  • In / out split: webhook for receive, Graph API for send; connect() wires both.
  • Retry-resistance: _dedup_wamid stops redelivery from producing duplicate replies.
  • Failure containment: a failed send() logs and moves on — one bad message never kills the loop.
  • Mention gating: only @-mentions get a reply in groups, keeping it a helper, not a spammer.

Self-Improving: Crystallizing Experience into Skills

What "self-improving" actually means

Hermes's self-improvement does not let the model edit its own source online. Two things happen instead, through two independent tools:

  • Procedural memory → a skill. When the agent works out a reusable way to do a task, it calls skill_manage(action="create") and writes a SKILL.md into ~/.hermes/skills/. Skills are narrow and actionable — "how to do X."
  • Declarative memory → MEMORY.md / USER.md. When the agent learns a fact, a user preference, or an environment detail, it calls the memory tool, which appends to MEMORY.md (observations) or USER.md (the user). This is broad and declarative — "what is true."

The agent gets smarter by accumulating both: vetted playbooks and a durable record of facts about the user and the world. It rewrites neither itself nor its core code.

"Self-Improving isn't about letting the agent edit its own code — it's about crystallizing experience into a skill, and facts into memory, through two separate tools."

How it triggers: the nudge

Neither tool fires on its own — the model decides. But Hermes runs two nudge counters in the background that periodically spawn a forked review agent to read recent conversation and decide what's worth saving:

  • Skill nudge counts tool-calling iterations. In agent/conversation_loop.py:2026 the counter _iters_since_skill ticks up each iteration; in agent/turn_finalizer.py:772 it fires when >= agent._skill_nudge_interval. The default interval is 10 (agent/agent_init.py:1956), read from skills.creation_nudge_interval.
  • Memory nudge counts user turns. In agent/turn_context.py:714 the counter _turns_since_memory ticks up per turn; it fires at >= agent._memory_nudge_interval. Same default 10 (agent/agent_init.py:1827), from memory.nudge_interval.

Both thresholds only summon a background review agent (prompt: agent/background_review.py:412 for skills, :401 for memory). That forked agent reads the conversation and decides whether to actually call skill_manage or memory. Reaching the count never writes a file by itself. Using either tool resets its own counter (agent/tool_executor.py:689-692).

The Curator: a later skill-ops layer

With skills being created, a question arises: who keeps the collection from rotting? That is the Curator (agent/curator.py, added 2026-04-26 — after skill_manage itself, 2026-02-19). It is not self-improvement; it is the maintenance layer on top of it: a background task that ages unused skills (active→stale→archived) and, optionally, merges narrow siblings into class-level "umbrella" skills. Its entry point run_curator_review (:1511) is a pure-function state machine:

def run_curator_review(
    on_summary=None, synchronous=False,
    dry_run=False, consolidate=None) -> Dict[str, Any]:

      1. Apply automatic state transitions (pure, no LLM).

         spawn a forked AIAgent for the LLM review prompt.
      3. Update .curator_state with last_run_at + summary.
      4. Invoke on_summary with a user-visible description.
    """
    if consolidate is None:
        consolidate = get_consolidate()   # OFF by default
    ...

The comment on step 2 is the key: "consolidate OFF by default" means the forked LLM review is skipped entirely on a normal run — only the deterministic inactivity prune runs. That is exactly why the default costs zero tokens. The remaining trade-offs fall out of the same shape:

  1. Zero LLM cost by default — the state machine itself never calls a model; tokens are spent only when genuine semantic judgment is required.
  2. dry-run previewable — it prints "what it will do" first, so you confirm before anything lands on disk.
  3. pinned skills are never touched — an explicitly pinned skill skips all automation, so curation can't flush content someone hand-wrote with care.
  4. Skills only — the Curator manages agent-created skills; it never touches memory files.

Takeaways

  • Not self-editing: the model never rewrites agent code; it produces skills and memory via two separate tools.
  • Two tools, decoupled: skill_manage writes procedural SKILL.md; memory writes declarative MEMORY.md / USER.md. Creating a skill never auto-writes memory.
  • Nudged, not spontaneous: skill nudge (10 tool iterations) and memory nudge (10 user turns) summon a background review agent that decides what to save.
  • Curator is ops, not core: added later, it only maintains agent-created skills — merge / age / archive — and never touches memory.

Long-Term Memory: Facts on Disk, Sessions in FTS5

Fact memory

Facts flow through MemoryManager → MemoryProvider — a background thread, serial, de-noised. The simplest implementation, MemoryStore (tools/memory_tool.py:159), writes MEMORY.md straight to disk via save_to_disk() (:387). The method itself is tiny; the safety lives in _write_file, which uses an atomic temp-file + rename so concurrent readers never see a half-written file:

def save_to_disk(self, target: str):
    """Persist entries to the appropriate file. Called after every mutation."""
    get_memory_dir().mkdir(parents=True, exist_ok=True)
    self._write_file(self._path_for(target), self._entries_for(target))

@staticmethod
def _write_file(path: Path, entries: List[str]):
    """Atomic temp-file + rename: readers see old OR new, never empty."""
    content = ENTRY_DELIMITER.join(entries) if entries else ""
    atomic_write_text(path, content, tmp_prefix=".mem_")

This is the durable "what I know about the user" store.

Session memory

The other track is conversational: hermes_state.py builds a full-text index with FTS5, including a CJK tokenizer messages_fts_cjk (:2685). That index is the foundation behind session_search — the ability to retrieve across past sessions, not just within one.

Writing safely under concurrency

The naive MemoryStore had a race: two reads of the file with a write between them could silently clobber an external edit. The fix reloads the target once, then runs both the drift check and the parse on that same snapshot — so an external write between operations can't be overwritten unnoticed. The add() path (:414) that calls save_to_disk() shows the real discipline: re-read from disk under a lock before mutating, reject exact duplicates, and refuse to write if the file read as empty (a transient blip that would otherwise wipe every prior memory):

def add(self, target, content):
    with self._file_lock(self._path_for(target)):
        if self._reload_target(target, skip_drift=True) is _READ_FAILED:
            return _read_failed_error(self._path_for(target))
        ...
        if content in entries:               # reject exact duplicate
            return self._success_response(target, "Entry already exists.")
        if new_total > limit:                # char-limit guard
            return self._consolidation_failure({...})
        entries.append(content)
        self._set_entries(target, entries)
        self.save_to_disk(target)            # durable write

Takeaways

  • Two tracks: facts go through MemoryManager → Provider (disk); sessions go through SessionDB + FTS5 (search).
  • FTS5 + CJK: messages_fts_cjk is what makes session_search work across sessions, including Chinese text.
  • Concurrency fixed: the write path now reloads once and checks drift + parses on one snapshot, closing the clobber race.
