消息网关：把平台与 Agent 彻底解耦

入口契约

每个平台适配器——Telegram、Discord、Slack、WhatsApp、Signal 等——都走同一条入口：gateway/platforms/base.py 里的 BasePlatformAdapter.handle_message。职责只有一个：把平台原始事件归一化成 MessageEvent，再交给 GatewayRunner._handle_message。Agent 从来看不到「Telegram 更新」和「WhatsApp webhook」的差别，只看到一条类型化的事件流。模块地图见官方 Gateway internals；本篇按一条消息走完对运维和贡献者最关键的路径。

该方法立刻返回：真正的一轮对话在后台 task 里跑，webhook 线程不会被模型卡住，控制类命令也能在 turn 进行中插进来。

async def handle_message(self, event: MessageEvent) -> None:
    if not self._message_handler:
        return
    if event.allow_gateway_control:
        coerce_plaintext_gateway_command(event)
    session_key = build_session_key(event.source, ...)
    # ... _process_message_background() -> GatewayRunner._handle_message(...)

有三点值得单独说清楚（不再是「两个细节……其三……」那种写法）。Handler 未挂载时直接 return，适配器可以先注册、后接线，消息在 handler 挂上之前只是空转。纯文本网关命令在 allow_gateway_control 为真时会被规整，没有原生斜杠的平台也能用 /stop 等。后台 spawn 才是双层 busy 守卫的前提：适配器可以在不死锁 webhook 的情况下排队或打断。

Session key

在鉴权和模型之前，适配器用 gateway/session.py 的 build_session_key() 派生 session_key——这是会话车道的唯一合法命名方式。不要手写拼接 ID；多 profile、线程、群里按人隔离，逻辑都在这个函数里。

布局（默认 profile 命名空间 main）：

agent:{namespace}:{platform}:{chat_type}[:{scope_id}][:{chat_id}][:{thread_id}][:{participant_id}]

例如 DM：agent:main:telegram:dm:123456789；在开启 group_sessions_per_user 的 Slack 群：agent:main:slack:group:C012345:U987654。Slack 会在 chat id 前插入 scope_id（工作区）；WhatsApp DM 会规范化号码；Discord 线程连续性可能把 chat_type 规范成 thread，让后续消息算出同一个 key。

两个配置项会传入每次调用：

  • group_sessions_per_user（默认开）——群里默认按发送者隔离，每人一条 agent 车道，除非你刻意共用一条会话。
  • thread_sessions_per_user（默认关）——论坛话题、Discord 线程、Slack 线程默认多人共享一条会话，除非你显式按人拆线程车道。

同一组（平台、会话、作用域）永远得到同一个 key。稳定性让 Gateway 能按车道缓存 agent、持久化会话、按车道挂 prompt cache 断点。见 Gateway session lifecycle 了解 SessionStore、session_id 轮换，以及不改变 key 的资源回收。

鉴权

Key 确定之后，GatewayRunner 判断发送者是否可以和 bot 对话。按顺序检查（先匹配到的倾向放行）；都不匹配则默认拒绝：

  1. 单平台 allow-all（如 TELEGRAM_ALLOW_ALL_USERS）
  2. 单平台 allowlist（如 TELEGRAM_ALLOWED_USERS）
  3. DM pairing——已授权用户 /pair 拿到码，新用户发送该码；状态在 gateway/pairing.py 持久化，重启不丢
  4. 全局 allow-all（GATEWAY_ALLOW_ALL_USERS / 配置里 gateway.allow_all_users）
  5. 默认：拒绝，不跑 agent turn

Pairing 适合没法预先铺用户 ID 的 DM 场景：bot 默认关闭，可信用户可以逐个拉人，不必改 env。生产群聊通常用 allowlist + @ 提及（平台相关），而不是 pairing。

GatewayRunner 流水线

gateway/run.py 的 GatewayRunner 由多个 mixin 拼成（run_inbound.py、run_turn.py、run_busy.py、run_agent_cache.py 等）。普通用户消息的路径是：

TurnRunner 管 agent 核心：按 session_key 拉历史、必要时跑工具审批、流式跑一轮对话循环、产出 final_response。适配器不 import agent 工具；runner 不解析 Telegram JSON。二十个平台不分叉 agent，靠的就是这道缝。

设计直觉：Gateway 不是 agent 的「前端」，而是「邮局」——投递 MessageEvent、发出回信；绝不替 agent 思考。

双层守卫、打断与排队

当一轮 turn 已在执行时，Hermes 用两道顺序守卫（官方 gateway internals 中的 Two-Level Message Guard）：

L1（gateway/platforms/base.py）：会话活跃时消息进 _pending_messages，并设置 interrupt 事件唤醒正在跑的 turn。L2（gateway/run_inbound.py + run_busy.py）：_running_agents 跟踪 live AIAgent。必须同步到达 runner 的命令用 await self._message_handler(event) 内联派发，避免和工具审批抢后台 task。

busy_input_mode（网关配置）决定 busy 时非命令消息怎么办：

  • interrupt（常见默认）——对 running agent 调 interrupt()，新用户文本成为转向输入；网关重启时未送达的 pending 可能丢弃。
  • queue——按会话 FIFO 追加（/queue 与 session state 里的 overflow）；在允许 drain 时重启后仍可续跑。
  • steer——走 running_agent.steer()，必要时扇出到活跃子 agent，避免粗暴 interrupt 破坏委托中的子任务。

体感：长任务跑着时贴一句纠正——interrupt 会 pivot；queue 可堆消息并用 /queue 看深度；/stop 任何模式都会硬停。压缩锁或活跃子 agent 可能把 interrupt 降级为 queue，避免父会话轮换中途被撕碎。

Delivery ledger

生成回复 ≠ 用户收到。gateway/delivery_ledger.py 在每次最终出站发送前后，于 state.db 记一条可恢复的投递义务（见 Messaging）：

  • record_obligation() — 第一次 send 前，状态 pending
  • mark_attempting() — await 前立刻标记
  • mark_delivered() / mark_failed() — 仅在明确的 SendResult 之后

语义是至少一次。模型已写完但 WhatsApp 还没确认时网关挂了，下次启动 sweep_recoverable() 会认领「原进程已死」的行，重发存好的正文，而不是整轮重跑（再付推理费）。进程仍活着时的 failed 行由带退避（30s / 2m / 10m）的重试 sweep 处理。线结果含糊时，恢复文案可能带前缀提示「可能是重复」——宁可提醒重复，也不静默丢答案。临时斜杠回复和空正文不进 ledger；接受崩溃丢回复可设 gateway.delivery_ledger: false。

熔断器

每个平台适配器外有一层熔断器。可重试失败反复出现——断连、限流、上游 5xx——会 trip：适配器暂停、打结构化日志，并可通知 home channel。与 delivery ledger（继续重试义务）不同，熔断器不会自动恢复；上游健康后需 /platform resume <platform> 手动恢复，避免长时间故障时疯狂重连。用 /platform list 和日志里的 circuit breaker、paused 排查。

Prompt cache 与 Gateway 为何拥有会话边界

Anthropic 式 prompt caching 在稳定前缀和滚动 transcript 尾部打 cache_control 标记（agent/prompt_caching.py）。默认布局是 system-and-3：最多四个断点——静态 system 前缀、system 末尾、以及最后三条可缓存的非 system 消息——若配置了 static_system_prefix 还会再拆 system 块。阈值与卫生层见 Context compression and caching。

Gateway 必须拥有 session_key 的原因：

  • Agent LRU 缓存（gateway/run_agent_cache.py）维护 session_key → AIAgent。复用实例让内存里的工具表和配置签名稳定；软淘汰会提交 memory，但不会换掉持久 transcript 的身份。
  • 缓存失效按 agent 实例全局生效——中途改 system 段、工具 schema 或模型路由会强制重建并冷写 cache。Gateway 每轮从 DB 读历史，但除非配置漂移，否则尽量不重建 agent。
  • 对平台无感的 agent——若错误共用 key，Telegram 和 Slack 会共用一条车道（不应发生）；每条车道有自己的 cached agent 和 cache 断点。多 profile 用命名空间（agent:work:…）避免互相污染前缀。

Gateway 会话卫生（约 85% 的 turn 前粗压）与 agent 内压缩（默认约 50%）是两层，但都假设 Gateway 已经决定打开哪条对话。Prompt caching 是经济上为何 agent 保持「每 turn 一次循环」，而 Gateway 管哪一条循环。

小结

  • 单一事件契约——适配器归一化为 MessageEvent；build_session_key() 命名车道。
  • 默认关闭——allowlist + DM pairing；除非某层显式放行。
  • Busy 是策略——双层守卫 + busy_input_mode；/stop、/queue 是一等公民。
  • 回复扛得住崩溃——delivery ledger 重发终稿；熔断器暂停病适配器。
  • 缓存跟着会话边界走——按 session_key 的 agent 缓存与 system-and-3；不要手写 key。

主要参考：Gateway internals、Session lifecycle、Messaging、Context compression and caching。

WhatsApp 接入：Cloud API、Webhook 与失败隔离

Cloud API 的形态

WhatsApp 用 webhook 收消息、用 Graph API 发消息。WhatsAppCloudAdapter.connect()（gateway/platforms/whatsapp_cloud.py:435）注册 webhook 校验握手与入站消息回调。校验通过后，每条用户消息以 webhook POST 到达，被归一化成 MessageEvent，流入第 1 篇讲的 GatewayRunner。真实代码里，它先拒绝启动（缺依赖或配置缺失就返回），再建两条传输——入站 webhook 服务、出站 httpx 客户端：

async def connect(self, *, is_reconnect: bool = False) -> bool:
    if not check_whatsapp_cloud_requirements():
        self._set_fatal_error("whatsapp_cloud_deps_missing", ...)
        return False
    if not self._phone_number_id or not self._access_token:
        self._set_fatal_error("whatsapp_cloud_unconfigured", ...)
        return False
    # Outbound HTTP client with tight keepalive.
    self._http_client = httpx.AsyncClient(
        timeout=30.0, limits=platform_httpx_limits())
    # Inbound webhook server next ...

注意开头的两道失败即停护栏：缺依赖、或 phone number id / token 没配，适配器在半启动前就停下。正是这份纪律，让一个配错的 bot 不会默默吞掉 webhook。

抗重试

Meta 的 webhook 会重复投递——一条消息可能到两三次。适配器用 _dedup_wamid（按平台消息 id 去重）守住，让一条消息绝不触发两次回复。没有它，每次抖动投递都会让你的 agent 答两遍（也多花一倍钱）。

抗错误扩散

当发给某接收者失败时，处理器只 log，不抛异常。一条发不出去的消息不该炸掉整个 webhook 处理循环，否则该适配器上的其他对话全黑。在边缘做隔离，才能避免一次坏发送连锁拖垮全部。

到底谁会被回复

在群里你不会想让机器人句句都答。适配器 mixin 里的 mention / allowlist 策略决定"只有被 @ 才回"，让它始终是个帮手而非垃圾机器人。这是每个话痨适配器都需要的同款模式；WhatsApp 因为群聊吵而格外显眼。

小结

  • 收发分离：webhook 收、Graph API 发；connect() 把两边接上。
  • 抗重试：_dedup_wamid 阻止重复投递产生重复回复。
  • 失败隔离：send() 失败只记日志不抛出——一条坏消息永不拖垮循环。
  • @ 门控：群里只有被 @ 才回，保持帮手定位，不做喷子。

自我进化：把经验固化为 Skill

"自我进化"到底指什么

Hermes 的自我进化不是让模型在线改自己的源码，而是经由两个相互独立的工具发生两件事：

  • 程序性记忆 → skill。当 agent 摸索出一种可复用的做法，它调 skill_manage(action="create")，把一个 SKILL.md 写进 ~/.hermes/skills/。skill 是窄而可执行的——"怎么做 X"。
  • 陈述性记忆 → MEMORY.md / USER.md。当 agent 学到一条事实、一条用户偏好或一个环境细节，它调 memory 工具，追加到 MEMORY.md（观察）或 USER.md（用户）。这是宽泛而陈述性的——"什么是真的"。

agent 是通过同时积累两者变聪明的：经过把关的 playbook加上一份关于用户和世界的持久事实记录。它既不改写自己，也不改写核心代码。

"Self-Improving 不是让 agent 改自己的代码，而是把经验固化为 skill、把事实写进记忆——通过两个独立的工具。"

怎么触发：nudge 计数器

两个工具都不会自己跑——由模型决定。但 Hermes 在后台跑两个 nudge 计数器，定期 fork 一个 review agent 去读最近的对话、判断什么值得存：

  • Skill nudge 计工具调用迭代轮数。在 agent/conversation_loop.py:2026 里计数器 _iters_since_skill 每轮 +1；在 agent/turn_finalizer.py:772 里当 >= agent._skill_nudge_interval 时触发。默认间隔是 10（agent/agent_init.py:1956），取自 skills.creation_nudge_interval。
  • Memory nudge 计user turn 数。在 agent/turn_context.py:714 里计数器 _turns_since_memory 每个 turn +1；到达 >= agent._memory_nudge_interval 时触发。默认同样是 10（agent/agent_init.py:1827），取自 memory.nudge_interval。

两个阈值都只是唤起一个后台 review agent（prompt：skill 在 agent/background_review.py:412，memory 在 :401）。那个 fork 出来的 agent 读对话、自己决定要不要真的调 skill_manage 或 memory。计数到了并不会自己写文件。用了任一工具就把自己这条计数器清零（agent/tool_executor.py:689-692）。

Curator：后来加的 skill 运维层

skill 会被不断创建，自然就有一个问题：谁保证这套收藏不腐烂？那就是 Curator（agent/curator.py，2026-04-26 加入——晚于 skill_manage 本身，2026-02-19）。它不是自我进化，而是架在上面的维护层：一个后台任务，把不用的 skill 按 active→stale→archived 老化，并在可选时把窄 sibling 合并成 class-level 的"umbrella" skill。入口 run_curator_review（:1511）是一个纯函数状态机：

def run_curator_review(
    on_summary=None, synchronous=False,
    dry_run=False, consolidate=None) -> Dict[str, Any]:
    """Execute a single curator review pass.
      1. Apply automatic state transitions (pure, no LLM).
      2. If consolidation enabled AND agent-created skills exist,
         spawn a forked AIAgent for the LLM review prompt.
      3. Update .curator_state with last_run_at + summary.
      4. Invoke on_summary with a user-visible description.
    """
    if consolidate is None:
        consolidate = get_consolidate()   # 默认 OFF
    ...

第 2 步的注释是关键："consolidate 默认 OFF" 意味着普通运行完全跳过 fork 出来的 LLM 评审——只跑确定性的闲置 prune。这正解释了为什么默认零 token。其余取舍都从同一结构里长出来：

  1. 默认零 LLM 成本——状态机本身不调模型，只有在真正需要语义判断时才花 token。
  2. dry-run 可预演——先打印"将要做什么"，确认无误再落盘。
  3. pinned skill 永不动——被显式钉住的 skill 跳过所有自动化，策展不会冲掉人工精心写的内容。
  4. 只管 skill——Curator 只维护 agent 创建的 skill，从不碰记忆文件。

小结

  • 不是自我改写：模型从不去改 agent 代码，它通过两个独立工具产出 skill 和记忆。
  • 两个工具，解耦：skill_manage 写程序性的 SKILL.md；memory 写陈述性的 MEMORY.md / USER.md。创建 skill 不会自动写记忆。
  • 靠 nudge，不靠自发：skill nudge（10 轮工具迭代）与 memory nudge（10 个 user turn）唤起后台 review agent 来决定存什么。
  • Curator 是运维，不是核心：后加的，只维护 agent 创建的 skill——合并/老化/归档——从不碰记忆。

长期记忆：事实落盘，会话进 FTS5

事实记忆

事实经 MemoryManager → MemoryProvider——后台线程、串行、去噪。最朴素的实现 MemoryStore（tools/memory_tool.py:159）通过 save_to_disk()（:387）把 MEMORY.md 直接落盘。方法本身很小；安全性在 _write_file：它用原子临时文件 + rename，并发读取者永远不会看到一个写一半的文件：

def save_to_disk(self, target: str):
    """Persist entries to the appropriate file. Called after every mutation."""
    get_memory_dir().mkdir(parents=True, exist_ok=True)
    self._write_file(self._path_for(target), self._entries_for(target))

@staticmethod
def _write_file(path: Path, entries: List[str]):
    """Atomic temp-file + rename: readers see old OR new, never empty."""
    content = ENTRY_DELIMITER.join(entries) if entries else ""
    atomic_write_text(path, content, tmp_prefix=".mem_")

这就是耐久的"我对用户已知什么"的存储。

会话记忆

另一条线是会话级的：hermes_state.py 用 FTS5 建全文索引，含 CJK 分词器 messages_fts_cjk（:2685）。这个索引是 session_search 的底座——能跨历史会话检索，而不只是单次会话内。

并发下的安全写入

朴素的 MemoryStore 曾有一个竞态：两次读文件中间夹一次写，可能静默覆盖外部编辑。修复是只重读一次目标，然后在同一份快照上同时做 drift 检测与解析——这样两次操作之间的外部写入不会被无察觉地覆盖。调用 save_to_disk() 的 add() 路径（:414）才露出真纪律：改动前在锁内重读磁盘、拒绝完全重复、若文件读成空（瞬时抖动，否则会清空所有历史记忆）则拒绝写：

def add(self, target, content):
    with self._file_lock(self._path_for(target)):
        if self._reload_target(target, skip_drift=True) is _READ_FAILED:
            return _read_failed_error(self._path_for(target))
        ...
        if content in entries:               # 拒绝完全重复
            return self._success_response(target, "Entry already exists.")
        if new_total > limit:                # 字符上限护栏
            return self._consolidation_failure({...})
        entries.append(content)
        self._set_entries(target, entries)
        self.save_to_disk(target)            # 耐久写入

小结

  • 两条线：事实走 MemoryManager → Provider（落盘）；会话走 SessionDB + FTS5（检索）。
  • FTS5 + CJK：messages_fts_cjk 让 session_search 能跨会话检索，含中文。
  • 修过并发：写入路径现在只重读一次、在同一快照上做 drift 检测与解析，堵住了被覆盖的竞态。
