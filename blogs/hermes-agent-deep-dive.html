Hermes Agent 架构深度解析

August 23, 2026

这是一篇基于 Hermes Agent 真实源码与 docs 的技术解析（仓库 hermes-agent），不是泛泛而谈的产品介绍。我会拆四个能力：Message Gateway（多平台消息网关）、WhatsApp 接入适配、Self-Improving（技能策展 / 自我进化）、Long-Term Memory（长期记忆如何落地）。每个能力都给：架构（Architecture）、流程图（Flow Chart，Mermaid）、核心方法分析（Key Method Analysis）。

阅读约定：中文为主，英文术语（类名 / 方法名）保留原样，方便对照源码。

0. 全景：Agent Core 与 Gateway 的分层

先建立心智模型。Hermes 的核心是一个 AIAgent 类（run_agent.py），它只负责“一次对话循环”。所有“从哪个聊天软件来、回哪个聊天软件去”的复杂度，都被推到 GatewayRunner（gateway/run.py，约 31k 行）和各平台 BasePlatformAdapter 子类里。

关键设计原则（来自 AGENTS.md）：Per-conversation prompt caching is sacred——每轮对话复用缓存前缀，任何中途改动 system prompt 或 tool schema 都会让缓存失效、成本翻倍。所以 Gateway 必须在“复用同一份 agent 实例”和“多会话隔离”之间精打细算。

1. Message Gateway（多平台消息网关）

1.1 架构 Architecture

入口契约是 BasePlatformAdapter.handle_message(event)（gateway/platforms/base.py:6045）。每个平台适配器（Telegram、Discord、Slack、WhatsApp、Signal…）都继承它。适配器把平台原始消息归一化成 MessageEvent，交给 GatewayRunner 的 _handle_message（gateway/run.py:16462）。

  • Adapter 层：平台协议、鉴权、媒体上传/下载、webhook 验证。set_message_handler() 注册回调（run.py:12847 等），把事件路由进 Gateway。
  • GatewayRunner：会话路由、命令解析、授权、活跃会话锁、工具审批流、流式输出。
  • TurnRunner（run.py:4291）：一次“用户消息 → agent 跑完 → 回包”的闭环执行器，通过 run_sync() 驱动。

1.2 流程图 Flow Chart

sequenceDiagram

1.3 核心方法分析 Key Method Analysis

(a) BasePlatformAdapter.handle_message — base.py:6045

这是“快速返回、后台处理”的典范。它立刻 spawn background tasks，目的有二：

  • 新消息可以在 agent 跑着的时候被接收（中断支持 / interruption）。
  • 一条消息处理卡住，不会阻塞同平台其他会话。

它会做 build_session_key() 把事件映射到会话身份（per-user / per-thread），并且有一个“自愈”逻辑：若 _active_sessions 残留一个已死亡的锁（split-brain，issue #11016），先 _heal_stale_session_lock() 清掉，再正常派发，避免用户被死守卫卡死。

(b) GatewayRunner._handle_message — run.py:16462

核心管线（源码 docstring 直译）：① 用户授权检查 → ② 命令检查（/new、/reset）→ ③ 若有运行中的 agent 则按策略中断 → ④ 获取/创建 session → ⑤ 构建 agent 上下文 → ⑥ 跑 agent 对话 → ⑦ 回包。

一个值得注意的细节：每个 handler 跑在 asyncio.create_task() 里，会 copy_context() 快照上下文。所以入口第一件事是 reset_session_vars()，把可能继承到的“兄弟会话的 HERMES_SESSION_* ContextVar”清空，防止跨会话泄漏（cross-session leak）。

(c) TurnRunner.run_sync — run.py:5348

真正的执行体。它做：platform→agent 的 platform hint 映射（Platform.LOCAL → "cli"）、合并四类 ephemeral prompt（事件渠道提示 + YAML 渠道提示 + 全局 ephemeral + gateway ephemeral）、解析 session 级 runtime（model / provider / service_tier / reasoning_config），最后把流式消费者（streaming TTS 等）接线好，交给 AIAgent.run_conversation。

2. WhatsApp 接入（WhatsApp Platform Adapter）

2.1 架构 Architecture

WhatsApp 有两套适配器：Cloud API（whatsapp_cloud.py，Meta 官方 Graph API + webhook）和基于 Baileys 的本地桥接（whatsapp_common.py 的 WhatsAppBehaviorMixin 是被两者共享的行为基类）。

共享行为抽在 WhatsAppBehaviorMixin（whatsapp_common.py:64）：mention 检测、allowlist 鉴权、DM 放行、群聊策略、文本清洗、分块上限。Cloud 适配器再继承 BasePlatformAdapter + 这个 mixin。

2.2 流程图 Flow Chart

flowchart TD
  M["Meta Webhook POST"] -->|"_handle_webhook"| V["_verify_signature HMAC-SHA256"]
  V -->|"ok"| D["_dispatch_payload"]
  D -->|"iterate entry/changes/messages"| AW["_dedup_wamid"]
  AW --> B["_build_message_event_from_cloud"]
  B -->|"_should_process_message"| H["handle_message"]
  H --> GR["GatewayRunner"]
  GR -->|"send / send_image / send_voice"| G["Meta Graph API messages"]
  G --> U["User on WhatsApp"]

2.3 核心方法分析 Key Method Analysis

(a) WhatsAppCloudAdapter.connect — whatsapp_cloud.py:435

连接分两半：

  • 出站：建一个 httpx.AsyncClient（30s 超时 + 收紧的 keepalive，对应 #18451，避免 CLOSE_WAIT 堆积）。
  • 入站：起一个 aiohttp webhook server（web.Application），挂三个路由——GET /health、GET /webhook（Meta 订阅握手 verify）、POST /webhook（收消息）。并发有 WEBHOOK_MAX_BODY_BYTES 上限兜底。

前置校验很“失败即弃（fail-closed）”：缺 WHATSAPP_CLOUD_PHONE_NUMBER_ID / ACCESS_TOKEN 直接 _set_fatal_error(retryable=False)；没 APP_SECRET 则拒绝所有入站 POST（503）。

(b) _dispatch_payload — whatsapp_cloud.py:1571

这是 webhook 的真正入口处理逻辑。它遍历 Meta 的 payload 结构 entry → changes → messages，但对每个 message 做了三件“抗脆弱”的事：

  • _dedup_wamid(wamid)：Meta 重试时会重发同一条，去重避免重复处理。
  • 构建事件失败 / dispatch 失败都 只 log，不抛出——否则 Meta 会重发整批（batch），把同批其它消息也当成重复丢掉。这是“把错误埋进日志、保住其它消息”的取舍。

(c) WhatsAppBehaviorMixin._should_process_message — whatsapp_common.py:390

决定“这条消息要不要喂给 agent”。逻辑覆盖：DM 放行名单（_is_dm_allowed）、群组是否需要 @提及（_message_mentions_bot / _message_is_reply_to_bot）、broadcast 群判断（_is_broadcast_chat）、以及把多个形式的 WhatsApp id（phone / LID）规整后做 allowlist 匹配（_matches_whatsapp_allowlist）。还支持 free_response_chats——某些群聊免 @直接回。

3. Self-Improving（自我进化：Curator 与 Skills）

3.1 架构 Architecture

Hermes 的“自我进化”主要通过 Skills（技能） 体系 + Curator（策展器） 后台维护实现，而不是让 agent 改自己的核心代码。

  • Skill：一个 SKILL.md（frontmatter + 步骤 + 坑点 + 验证）。可被 skills_list / skill_view 检索加载。agent 在任务中“学会”的东西，优先固化成 skill。
  • Curator（agent/curator.py）：后台定期运行的“技能管理员”。它做生命周期迁移（active → stale → archived）和可选的 LLM 合并（把一堆窄 skill 合并成 class-level 的 umbrella skill）。

3.2 流程图 Flow Chart

flowchart TD
  T["Timer / Inactivity"] --> R["run_curator_review"]
  R --> S["apply_automatic_transitions (pure, no LLM)"]
  S -->|"stale / archive"| ST[".curator_state"]
  R -->|"consolidate ON"| L["spawn forked AIAgent (LLM merge)"]
  L -->|"REPORT / merge"| SK["~/.hermes/skills"]
  R -->|"dry_run"| REP["REPORT.md (report only)"]
  SK --> U["Agent later loads"]

3.3 核心方法分析 Key Method Analysis

(a) run_curator_review — agent/curator.py:1511

单次策展的步骤（来自 docstring）：① 先跑 纯函数 apply_automatic_transitions()（按真实 activity 时间戳做状态迁移，无 LLM、零成本）；② 若开启 consolidate 且存在 agent 创建的 skill，则 spawn 一个 forked AIAgent 跑 LLM 合并 prompt；③ 更新 .curator_state（last_run_at + 摘要）；④ 通过 on_summary 给用户可见的总结。

关键工程取舍：

  • 默认 consolidate = OFF（DEFAULT_CONSOLIDATE = False，curator.py:78）→ 只跑确定性的“按不活跃 prune”，完全跳过 aux-model 调用，省成本。
  • dry_run：跳过状态迁移，只写 REPORT.md 告诉你“我会做什么”，不真正改任何 skill——安全的预演。
  • 运行前先 curator_backup.snapshot_skills() 做快照（best-effort），即使中途崩，状态也记录了。

(b) 只动 agent 创建的 skill

策展的边界很明确：只迁移 tools.skill_usage.is_agent_created 标记的 skill；pinned（被钉住）的 skill 永远不动；被 cron job 引用的 skill 也当 pinned 对待，防止“一次性任务”的 skill 被自动老化掉（_cron_referenced_skills()）。Hub-installed 的 skill 永不 prune。

(c) LLM 合并的提示词约束

给 forked agent 的 prompt 明确禁止它直接调用 skill_manage（patch/create/delete）或用 terminal 去 mv 目录——所有变更必须经过策展器的确定性强转路径（curator.py:412 附近）。这避免了“LLM 自己乱改文件系统”的失控。设计哲学（docstring 原话）：技能的终极目标是 CLASS-LEVEL 的图书馆——那种“一个 bug 对应一个窄 skill”是失败的，应该合并。

4. Long-Term Memory（长期记忆如何落地）

4.1 架构 Architecture

Hermes 的记忆分两层，别混为一谈：

  • 会话记忆（Session Memory）：SessionDB（hermes_state.py），SQLite + FTS5 全文索引，存每一次对话消息，支持跨会话检索（session_search）。
  • 长期事实记忆（Long-Term / Factual Memory）：MemoryManager（agent/memory_manager.py）+ 插件式 MemoryProvider（agent/memory_provider.py，如 honcho / mem0 / supermemory）。外加一个轻量的本地 MemoryStore（tools/memory_tool.py）落盘到 MEMORY.md / USER.md。

4.2 流程图 Flow Chart

flowchart TD
  U["User message"] --> Ag["AIAgent.run_conversation"]
  Ag --> MM["MemoryManager"]
  MM -->|"prefetch_all into system prompt"| Ag
  Ag -->|"turn ends"| MM
  MM -->|"sync_all (background thread)"| MP["MemoryProvider.sync_turn"]
  MP -->|"persist"| BE["Backend: mem0 / honcho / ..."]
  AG["memory_tool add/replace/remove"] --> MS["MemoryStore"]
  MS -->|"save_to_disk"| F["MEMORY.md / USER.md"]
  Ag -->|"each turn"| SD["SessionDB + FTS5"]

4.3 核心方法分析 Key Method Analysis

(a) MemoryManager.sync_all — agent/memory_manager.py:675

这是“长期事实记忆”的写入关隘。它把已完成的回合（completed turn）同步到所有 provider。关键设计：绝不内联（inline）跑——而是 _submit_background(_run) 派发到后台 worker 线程。原因（源码注释）：曾经一个 misconfigured 的 Hindsight daemon 阻塞了 ~298s，导致 run_conversation 在用户已看到回复后还卡着，所有界面都显示 agent “running”，后续消息还会触发激进中断。后台化后，慢/坏 provider 永远卡不住主流程。

写入还被单 worker 串行化，保证 turn N 先于 N+1 落地；provider 自己无需保证顺序。另外会先 _strip_skill_scaffolding 剥掉 skill 脚手架噪声再写，避免污染长期记忆。

(b) MemoryProvider.sync_turn — agent/memory_provider.py:201

插件式 provider 的抽象方法。签名暴露了它拿到的全部上下文：user_content、assistant_content、session_id，以及完整的 OpenAI 风格 messages 列表（含 tool calls / tool results）。注释强调它应是非阻塞的（有延迟就排队）。每个 provider（mem0 / honcho / supermemory）自己决定怎么 embedding、怎么去重、怎么形成长期知识。

(c) MemoryStore（本地落盘）— tools/memory_tool.py:159

这是“最朴素的长期记忆”：直接写 Markdown 文件。两条目标：

  • MEMORY.md：agent 的一般性记忆（general facts）。
  • USER.md：关于用户的事实（user facts）。

细节工程：

  • 每次变更后 save_to_disk() 落盘（memory_tool.py:387）。
  • _reload_target() 在变更前重新读盘、用同一份 raw 快照同时做 drift 检测 + 解析（memory_tool.py:381）——修掉过一个竞态：旧的 drift 检测会二次读文件，两次读之间外部写入的内容会被静默覆盖（overwrite）。一次读、一份快照、无窗口。
  • add() 是追加（append），所以跳过 drift guard 也不会覆盖既有内容；而 replace/remove/apply_batch 会重写文件，必须过 drift 检测，否则放弃本次变更（避免把外部进程刚写的内容抹掉）。

(d) SessionDB + FTS5

会话记忆是可检索的：hermes_state.py 用 CREATE VIRTUAL TABLE ... USING fts5(...) 建全文索引（含 CJK 专用 tokenizer messages_fts_cjk，hermes_state.py:2685）。这就是 session_search 能“跨会话 FTS5 检索历史消息”的底座。源码里还有一大段 FTS5 索引腐化检测/重建逻辑（#50502、v23 marker），说明这块在生产里踩过不少坑。

5. 小结 Takeaways

  • Gateway 的本质：把“平台协议复杂度”和“agent 核心循环”彻底解耦。Adapter 归一化事件 → GatewayRunner 做会话/授权/命令 → TurnRunner 跑闭环。整个设计围绕“prompt caching 不可破坏”这条铁律。
  • WhatsApp：Cloud API 用 webhook + Graph API；抗重试靠 _dedup_wamid，抗错误扩散靠“dispatch 失败只 log 不抛”，谁该被回复靠 mixin 里的 mention/allowlist 策略。
  • Self-Improving：不是让 agent 改自己代码，而是把经验固化为 skill，由 Curator 用“纯函数状态机 + 可选 LLM 合并”做后台管家，且默认零 LLM 成本、dry-run 可预演、pinned 永不动。
  • Long-Term Memory：事实记忆走 MemoryManager → MemoryProvider（后台线程、串行、去噪），会话记忆走 SessionDB + FTS5；最朴素的 MemoryStore 直接落 MEMORY.md，并在 drift 检测上修过竞态。
