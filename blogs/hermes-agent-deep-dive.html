Hermes Agent Architecture, Deep Dive

A source-grounded tour of how a personal AI agent decouples multi-platform messaging from a single conversation loop — and how it evolves and remembers on its own.

DL
By Daniel Liu · August 23, 2026 · 12 min read

This is a technical breakdown based on the real source and docs of Hermes Agent (repo hermes-agent) — not a vague product pitch. We'll take apart four capabilities: Message Gateway (the multi-platform message bus), WhatsApp integration, Self-Improving (skill curation / self-evolution), and Long-Term Memory (how memory actually lands on disk). For each, I give the architecture, the core-method analysis, and the real coordinates I dug out of the source (file:line).

0. The Big Picture: Agent Core vs. Gateway

Let's build the mental model first. Hermes's core is an AIAgent class (run_agent.py) that owns only "one conversation loop." All the complexity of "which chat app did this come from / which chat app should the reply go to" is pushed out into GatewayRunner (gateway/run.py, ~31k lines) and the per-platform BasePlatformAdapter subclasses.

The key design principle (from AGENTS.md): Per-conversation prompt caching is sacred — every turn reuses a cached prefix, and any mid-conversation change to the system prompt or the tool schema invalidates that cache and doubles the user's cost. So the Gateway has to carefully balance "reuse one agent instance" against "isolate per session."

1. Message Gateway (the multi-platform bus)

The entry contract is BasePlatformAdapter.handle_message(event) (gateway/platforms/base.py:6045). Every platform adapter — Telegram, Discord, Slack, WhatsApp, Signal, … — extends it. The adapter normalizes the platform's raw message into a MessageEvent and hands it to GatewayRunner._handle_message (gateway/run.py:16462).

Inside, GatewayRunner splits into two layers: a session-routing layer (find/create a session by session_key, an active-session lock, the tool-approval flow) and the TurnRunner (gateway/run.py:5348, which actually runs one agent loop, streams output, and feeds tool results back). This split keeps "platform protocol complexity" and "agent core logic" from contaminating each other.

Design intuition: the Gateway isn't the agent's "frontend" — it's the agent's "post office." It only delivers the letter (MessageEvent) correctly and sends the reply (final_response) correctly. It never thinks for the agent.

2. WhatsApp Integration

WhatsApp rides Meta's Cloud API: a webhook receives messages → the Graph API sends them. WhatsAppCloudAdapter.connect() (gateway/platforms/whatsapp_cloud.py:435) registers the webhook verification and the message callback. Three engineering details are worth noting:

  • Retry-resistance: Meta's webhook redelivers, so _dedup_wamid deduplicates and stops one message from triggering two replies.
  • Failure-containment: a dispatch failure only logs — it does not throw. One undeliverable message shouldn't crash the entire webhook loop.
  • Who gets a reply: a mention / allowlist policy in the mixin decides "only reply when @-mentioned in a group," so it never becomes a spam bot.
"Self-Improving isn't about letting the agent edit its own code — it's about crystallizing experience into a skill."

3. Self-Improving (self-evolution)

This is the most commonly misread part. Hermes's "self-improvement" does not let the model edit source online. Instead, it crystallizes reusable experience into a skill (procedural knowledge in SKILL.md form), stewarded in the background by the Curator.

agent/curator.py's run_curator_review (:1511) is a pure-function state machine: it scans existing skills, decides whether to merge / archive / update, and optionally calls an LLM for "semantic merge." The key trade-offs:

  1. Zero LLM cost by default — the state machine itself never calls a model; tokens are only spent when genuine semantic judgment is needed.
  2. dry-run previewable — it prints "what it will do" first, so you confirm before anything lands.
  3. pinned skills are never touched — an explicitly pinned skill skips all automation, so curation can't flush content someone hand-wrote with care.

4. Long-Term Memory

Memory runs on two tracks. One is fact memory: MemoryManager → MemoryProvider (background thread, serial, de-noised); the simplest MemoryStore (tools/memory_tool.py:159) writes MEMORY.md straight to disk (save_to_disk() @ :387). The other is session memory: hermes_state.py builds a full-text index with FTS5 (including a CJK tokenizer, messages_fts_cjk, :2685) — that's the foundation behind session_search's cross-session retrieval.

5. Takeaways

  • The Gateway's essence: it fully decouples "platform protocol complexity" from the "agent core loop," and the whole design orbits the iron rule that "prompt caching must not be broken."
  • WhatsApp: Cloud API + webhook + Graph API; retry-resistance via _dedup_wamid, failure-containment via "dispatch failure logs, doesn't throw."
  • Self-Improving: experience → skill; the Curator is a "pure-function state machine + optional LLM merge" background steward — zero-cost by default, previewable, pinned untouched.
  • Long-Term Memory: facts go through MemoryManager → Provider, sessions go through SessionDB + FTS5; the simplest MemoryStore writes to disk directly and had its write race fixed on the drift check.
