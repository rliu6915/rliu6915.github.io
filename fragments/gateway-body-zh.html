入口契约

每个平台适配器——Telegram、Discord、Slack、WhatsApp、Signal 等——都走同一条入口：gateway/platforms/base.py 里的 BasePlatformAdapter.handle_message。职责只有一个：把平台原始事件归一化成 MessageEvent，再交给 GatewayRunner._handle_message。Agent 从来看不到「Telegram 更新」和「WhatsApp webhook」的差别，只看到一条类型化的事件流。模块地图见官方 Gateway internals；本篇沿事件到送达回信的路径，讲清五块机制：会话、鉴权、命令、排队、投递。

该方法立刻返回：真正的一轮对话在后台 task 里跑，webhook 线程不会被模型卡住，控制类命令也能在 turn 进行中插进来。

async def handle_message(self, event: MessageEvent) -> None:
    if not self._message_handler:
        return
    if event.allow_gateway_control:
        coerce_plaintext_gateway_command(event)
    session_key = build_session_key(event.source, ...)
    # ... _process_message_background() -> GatewayRunner._handle_message(...)

有三点值得单独说清楚。Handler 未挂载时直接 return，适配器可以先注册、后接线，消息在 handler 挂上之前只是空转。纯文本网关命令在 allow_gateway_control 为真时会被规整，没有原生斜杠的平台也能用 /stop 等。后台 spawn 才是双层 busy 守卫的前提：适配器可以在不死锁 webhook 的情况下排队或打断。

会话：key、SessionStore 与 agent 缓存

在鉴权和模型之前，适配器用 gateway/session.py 的 build_session_key() 派生 session_key——这是会话车道的唯一合法命名方式（runner 内通过 _session_key_for_source() 调用）。不要手写拼接 ID；多 profile、线程、群里按人隔离，逻辑都在这个函数里。完整 key 规则见 Gateway session lifecycle。

布局（默认 profile 命名空间 main）：

agent:{namespace}:{platform}:{chat_type}[:{scope_id}][:{chat_id}][:{thread_id}][:{participant_id}]

例如 DM：agent:main:telegram:dm:123456789；在开启 group_sessions_per_user 的 Slack 群：agent:main:slack:group:C012345:U987654。同一组（平台、会话、作用域）永远得到同一个 key，Gateway 才能按车道缓存 agent、持久化会话、按车道挂 prompt cache 断点。

SessionStore（gateway/session.py）把稳定的 session_key 映射到可轮换的 session_id（YYYYMMDD_HHMMSS_<8hex>）。元数据在 sessions.json；transcript 与持久化会话行在 SQLite 的 SessionDB 里。每条入站消息会走 get_or_create_session()：

  • suspended=True（/stop 或 stuck-loop 升级）→ 硬擦除：下次访问换新 session_id。
  • resume_pending=True（崩溃恢复、drain 超时）→ 保留原 session_id 与 transcript；下一轮成功 turn 后清除标记。
  • 否则 → 更新 updated_at，继续同一 incarnation，直到 /new、/reset 或显式策略要求重置。

资源回收（TTL、LRU 路由项修剪、内存压力 sweep）只释放缓存，不改变 key、也不结束持久 transcript——仅靠空闲时间不会轮换对话。

Agent LRU 缓存（gateway/run_agent_cache.py）是第二条索引：session_key → AIAgent。命中则复用同一内存实例（工具表、配置签名、prompt cache 热度）；未命中则新建，并可能按 LRU 淘汰（默认上限 128）。淘汰走 _commit_then_release_soft：memory provider 刷盘、客户端释放，但 SQLite transcript 与 session_id 不变，下轮可继续。正在 turn 的 agent、受保护的近期车道、以及 transcript 尚未落盘对齐的会话不会被 shed。因此会话边界必须由 Gateway 持有，而不是 agent 自己拼 key。

两个配置项会传入每次 build_session_key()：

  • group_sessions_per_user（默认开）——群里默认按发送者隔离，每人一条 agent 车道，除非你刻意共用一条会话。
  • thread_sessions_per_user（默认关）——论坛话题、Discord 线程、Slack 线程默认多人共享一条会话，除非你显式按人拆线程车道。

鉴权

Key 确定之后，GatewayRunner 判断发送者是否可以和 bot 对话。按顺序检查（先匹配到的倾向放行）；都不匹配则默认拒绝——不跑 agent turn：

  1. 单平台 allow-all（如 TELEGRAM_ALLOW_ALL_USERS）
  2. 单平台 allowlist（如 TELEGRAM_ALLOWED_USERS）
  3. DM pairing——状态在 gateway/pairing.py 持久化，重启不丢
  4. 全局 allow-all（GATEWAY_ALLOW_ALL_USERS / 配置里 gateway.allow_all_users，由 gateway/config_loader.py 桥接）
  5. 默认：拒绝

DM pairing 流程（见 Gateway internals）：已授权用户执行 /pair 获得短码；新用户把该码作为普通消息发送；匹配后其平台用户 id 写入 pairing 存储，之后视同 allowlist 用户。适合无法预先铺员工 ID 的 DM：默认关闭，逐个拉人，不必改 env。生产群聊通常用 allowlist + @ 提及，而不是 pairing。

斜杠命令：解析与 busy 策略

网关斜杠命令共用一条流水线（Gateway internals 中 Slash Command Dispatch）：

  1. hermes_cli/commands.py 的 resolve_command() 把用户输入映射为规范命令名（别名、前缀匹配）。
  2. 规范名须出现在 GATEWAY_KNOWN_COMMANDS 中。
  3. gateway/run_inbound.py 的 _handle_message() 通过 gateway/slash_commands_*.py mixin 上的 _handle_<name>_command 查找处理器，表由 gateway/run_busy.py 的 _IDLE_COMMANDS / _PLAIN_COMMANDS 构建为 _command_handler_table——不是一长串 if canonical == ...。
  4. CommandDef 上的可选 gateway_config_gate 在功能关闭时跳过处理器。

当 session_key 已在 _running_agents 中时，_dispatch_busy_slash_command() 按各命令的 CommandDef.busy_policy 与可选 busy_handler（_busy_<name>_command）路由：执行 mid-turn 变体、在 policy 允许时执行普通处理器，或回复拒绝（「Agent 正在运行——…不能 mid-turn 执行」）。

Bypass 命令——/stop、/new、/approve、/deny、/queue、/status——有 mid-run 处理器，必须同步到达 runner。适配器 L1 与 runner L2 用 await self._message_handler(event) 内联派发，而不是再开后台 task，避免与工具审批抢 race、也避免「一直 busy」死锁。

GatewayRunner 流水线

gateway/run.py 的 GatewayRunner 由多个 mixin 拼成（run_inbound.py、run_turn.py、run_busy.py、run_agent_cache.py 等）。普通用户消息的路径是：

TurnRunner 管 agent 核心：按 session_key 拉历史、必要时跑工具审批、流式跑一轮对话循环、产出 final_response。适配器不 import agent 工具；runner 不解析 Telegram JSON。二十个平台不分叉 agent，靠的就是这道缝。

设计直觉：Gateway 不是 agent 的「前端」，而是「邮局」——投递 MessageEvent、发出回信；绝不替 agent 思考。

排队：双层 pending 与 /queue FIFO

当一轮 turn 已在执行时，Hermes 用两道顺序守卫，以及两种不同的排队语义（见 gateway internals 与 session lifecycle 中的 Two-Level Message Guard、Message Queuing Flow）：

L1（gateway/platforms/base.py）：会话活跃时，消息进入每会话单槽 _pending_messages（突发合并——第二条会覆盖槽位），并设置 interrupt 事件唤醒正在跑的 turn。L2（gateway/run_inbound.py + run_busy.py）：_running_agents 跟踪 live AIAgent，对非命令文本应用 busy_input_mode。

FIFO /queue 与 interrupt 跟进不同。每次 /queue 必须各自产生一整轮 agent turn，按序、不合并。run_busy.py 的 _enqueue_fifo() 在槽位空闲时放入事件；槽位占用时追加到 _queued_events[session_key]。每次 drain 后 _promote_queued_event() 把溢出队列头推进槽位。_queue_depth() 返回 len(overflow) + (槽位是否占用 ? 1 : 0)——即 /queue 向运维展示的深度。/new、/reset 会清掉排队的人类跟进；为 async delegation 固定的内部 wake 事件按设计可能保留。

busy_input_mode（网关配置）决定 busy 时非命令消息怎么办：

  • interrupt（常见默认）——对 running agent 调 interrupt()，新用户文本成为转向输入；槽位 pending 可能在网关重启时丢失。
  • queue——在配置允许时接近显式 /queue 语义；启用 drain-on-shutdown 时重启后可续跑。
  • steer——走 running_agent.steer()，必要时扇出到活跃子 agent，避免粗暴 interrupt 破坏委托中的子任务。

压缩锁或活跃子 agent 可能把 interrupt 降级为 queue，避免父会话轮换中途被撕碎。体感：长任务跑着时贴纠正——interrupt 会 pivot；queue 模式可堆任务；/stop 任何模式都会硬停。

投递：delivery.py 与 ledger

生成回复 ≠ 用户收到。gateway/delivery.py 负责出站路由（Gateway internals 中 Delivery Path）：

  • 直接回复——经来源平台适配器与原 chat 送回。
  • Home channel——cron 与后台结果发到各平台配置的 home channel。
  • 显式目标——如 telegram:-1001234567890，供 hermes send 与 cron deliver: 使用。
  • 跨平台——投递到与入站不同的平台（路由依赖 SessionStore 中的会话上下文）。

Cron 投递故意不镜像进 gateway 会话历史，只留在 cron 自己的会话里，避免角色交替违规。

每次最终平台 send 前后，gateway/delivery_ledger.py 在 state.db 记录可恢复义务（用户向语义见 Messaging）：

  • record_obligation() — 第一次 send 前，状态 pending
  • mark_attempting() — await 前立刻标记
  • mark_delivered() / mark_failed() — 仅在明确的 SendResult 之后

语义是至少一次。模型已写完但 WhatsApp 还没确认时网关挂了，下次启动 sweep_recoverable() 会认领「原进程已死」的行，重发存好的正文，而不是整轮重跑。进程仍活着时的 failed 行由带退避（30s / 2m / 10m）的重试 sweep 处理。线结果含糊时，恢复文案可能带重复提示前缀。临时斜杠回复和空正文不进 ledger；接受崩溃丢回复可设 gateway.delivery_ledger: false。活跃 turn 标记与会话恢复协同：已持久化但未 ledger 的回复会变成可恢复行，而不是第二次完整推理。

熔断器

每个平台适配器外有一层熔断器。可重试失败反复出现——断连、限流、上游 5xx——会 trip：适配器暂停、打结构化日志，并可通知 home channel。与 delivery ledger（继续重试义务）不同，熔断器不会自动恢复；上游健康后需 /platform resume <platform> 手动恢复，避免长时间故障时疯狂重连。用 /platform list 和日志里的 circuit breaker、paused 排查。

Prompt cache 与 Gateway 为何拥有会话边界

Anthropic 式 prompt caching 在稳定前缀和滚动 transcript 尾部打 cache_control 标记（agent/prompt_caching.py）。默认布局是 system-and-3：最多四个断点——静态 system 前缀、system 末尾、以及最后三条可缓存的非 system 消息——若配置了 static_system_prefix 还会再拆 system 块。阈值与卫生层见 Context compression and caching。

经济上的理由与会话一节呼应：

  • 按 session_key 复用缓存的 AIAgent，让断点跨 turn 保持温热。
  • 缓存失效按 agent 实例全局生效——改 system、工具 schema 或模型路由会强制重建并冷写。
  • 多 profile 用命名空间（agent:work:…）避免互相污染前缀。

Gateway 会话卫生（约 85% 的 turn 前粗压）与 agent 内压缩（默认约 50%）是两层，但都假设 Gateway 已经决定打开哪条对话。

小结

  • 会话——build_session_key() 命名车道；SessionStore 映射 session_id 与 SQLite transcript；run_agent_cache.py 按 key LRU 复用 AIAgent。
  • 鉴权——有序放行层；DM pairing 在 pairing.py，默认关闭的 DM 入口。
  • 命令——resolve_command() + 命令表；turn 进行中靠 busy_policy 与内联 bypass。
  • 排队——适配器单槽 + runner busy 策略；/queue 经 _queued_events FIFO，一项一整轮。
  • 投递——delivery.py 路由出站；delivery_ledger.py 让终稿在崩溃后至少送达一次。
