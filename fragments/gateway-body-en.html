The entry contract

Every platform adapter — Telegram, Discord, Slack, WhatsApp, Signal, and the rest — funnels through one method: BasePlatformAdapter.handle_message in gateway/platforms/base.py. Its job is to normalize whatever the platform handed you into a MessageEvent and forward it to GatewayRunner._handle_message. The agent never sees “Telegram update” versus “WhatsApp webhook”; it only sees a typed event stream. The Gateway internals doc maps the surrounding files; this chapter walks the five mechanisms that sit between that event and a delivered reply: session, auth, commands, queue, and delivery.

The handler returns immediately: adapters spawn the real turn in a background task so inbound webhooks do not block and control commands can still reach the runner while a model turn is in flight.

async def handle_message(self, event: MessageEvent) -> None:
    if not self._message_handler:
        return
    if event.allow_gateway_control:
        coerce_plaintext_gateway_command(event)
    session_key = build_session_key(event.source, ...)
    # ... _process_message_background() -> GatewayRunner._handle_message(...)

Three behaviors worth naming explicitly. Early return when _message_handler is unset lets adapters register before the runner wires up — messages no-op until the handler exists. Gateway commands in plain text are coerced when allow_gateway_control is true, so /stop and friends work even on platforms without native slash commands. Background spawn is what makes the dual-layer busy guard possible: the adapter can queue or interrupt without deadlocking the webhook thread.

Session: key, SessionStore, and agent cache

Before authorization or model work, the adapter derives a session_key with build_session_key() in gateway/session.py — the only supported way to name a conversation lane (via _session_key_for_source() inside the runner). Never concatenate IDs by hand; multiplexing, threads, and per-user group isolation all live in that function. See Gateway session lifecycle for the full key matrix.

Layout (default profile namespace main):

agent:{namespace}:{platform}:{chat_type}[:{scope_id}][:{chat_id}][:{thread_id}][:{participant_id}]

Examples: agent:main:telegram:dm:123456789 for a DM; agent:main:slack:group:C012345:U987654 when group_sessions_per_user isolates speakers in a channel. The same triple (platform, chat, scope) always yields the same key. That stability is what lets the gateway cache agents, persist sessions, and attach prompt-cache breakpoints per lane.

SessionStore (gateway/session.py) maps each stable session_key to a rotating session_id (YYYYMMDD_HHMMSS_<8hex>). Metadata lives in sessions.json; transcripts and durable session rows live in SQLite via SessionDB. On each inbound message the runner calls get_or_create_session():

  • suspended=True (from /stop or stuck-loop escalation) → hard wipe: new session_id on next access.
  • resume_pending=True (crash recovery, drain timeout) → preserve the existing session_id and transcript; cleared after the next successful turn.
  • Otherwise → bump updated_at and continue the same incarnation until /new, /reset, or explicit policy says otherwise.

Housekeeping (TTL, LRU routing-entry prune, memory-pressure sweeps) reclaims cached resources without changing the key or ending the durable transcript — idle time alone never rotates a conversation.

Agent LRU cache (gateway/run_agent_cache.py) holds a second index: session_key → AIAgent. A cache hit reuses the same in-memory instance (tool registry, config signature, prompt-cache warmth); a miss constructs a new agent and may evict the least-recently-used entry (default cap 128). Eviction runs _commit_then_release_soft: memory providers flush, clients detach, but the SQLite transcript and session_id stay put for the next turn. Mid-turn agents, protected-recent lanes, and sessions whose transcript has not caught up to disk are never shed. This cache is why the gateway — not the agent — must own the session boundary.

Two knobs from config flow into every build_session_key() call:

  • group_sessions_per_user (default on) — in groups, append the sender so each human gets a private agent lane unless you intentionally share one session.
  • thread_sessions_per_user (default off) — forum topics, Discord threads, and Slack threads stay shared across participants unless you opt into per-user thread lanes.

Authorization

After the key is known, GatewayRunner evaluates whether this sender may talk to the bot. Checks run in order (first match wins toward allow); anything unmatched falls through to deny — no agent turn, no pairing bypass for group spam:

  1. Per-platform allow-all (e.g. TELEGRAM_ALLOW_ALL_USERS)
  2. Per-platform allowlist (e.g. TELEGRAM_ALLOWED_USERS)
  3. DM pairing — persisted in gateway/pairing.py (survives restarts)
  4. Global allow-all (GATEWAY_ALLOW_ALL_USERS / gateway.allow_all_users in config, bridged from gateway/config_loader.py)
  5. Default: reject

DM pairing flow (from Gateway internals): an already-authorized user runs /pair; the gateway returns a short code; the newcomer sends that code as a plain message; on match, their platform user id is written to the pairing store and they are treated like an allowlisted user thereafter. Pairing is the escape hatch when you cannot pre-seed employee IDs for DMs — closed by default, onboard one human at a time without editing env files. Production group bots typically combine allowlists with mention gating instead.

Slash commands: resolve and busy policy

Gateway slash commands share one pipeline (documented under “Slash Command Dispatch” in Gateway internals):

  1. resolve_command() in hermes_cli/commands.py maps user text to a canonical name (aliases, prefix matching).
  2. The canonical name must appear in GATEWAY_KNOWN_COMMANDS.
  3. _handle_message() in gateway/run_inbound.py looks up _handle_<name>_command on the gateway/slash_commands_*.py mixins via _command_handler_table built from _IDLE_COMMANDS / _PLAIN_COMMANDS in gateway/run_busy.py — not a long if canonical == ... chain.
  4. Optional gateway_config_gate on CommandDef skips handlers when config disables a feature.

While session_key is present in _running_agents, _dispatch_busy_slash_command() routes by each command’s CommandDef.busy_policy and optional busy_handler (_busy_<name>_command): run the mid-turn variant, run the normal handler if policy allows, or reply with a reject (“Agent is running — … can’t run mid-turn”).

Bypass commands — /stop, /new, /approve, /deny, /queue, /status — have mid-run handlers and must reach the runner synchronously. Level 1 in the adapter and Level 2 in the runner dispatch them with await self._message_handler(event) instead of another background task, avoiding races with tool approval and stuck “busy” deadlocks.

TurnRunner owns the agent core: load history for this session_key, run tool approval if needed, stream one conversation loop, return final_response. Protocol adapters never import agent tools; the runner never parses Telegram JSON. That split is what keeps twenty platforms from forking the agent.

Design intuition: the Gateway is not the agent’s “frontend” — it is the agent’s post office. It delivers the letter (MessageEvent) and sends the reply; it does not think for the agent.

Queue: dual-layer pending and /queue FIFO

When a turn is already running, Hermes uses two sequential guards plus two different queue semantics (see “Two-Level Message Guard” and “Message Queuing Flow” in gateway internals and session lifecycle):

Level 1 (gateway/platforms/base.py): if the session is active, the message lands in the per-session single slot _pending_messages (burst collapse — a second message overwrites the slot) and an interrupt event wakes the in-flight turn. Level 2 (gateway/run_inbound.py + run_busy.py): _running_agents tracks the live AIAgent and applies busy_input_mode to non-command text.

FIFO /queue is separate from interrupt follow-ups. Each /queue invocation must produce exactly one full agent turn, in order, without merging. _enqueue_fifo() in run_busy.py places the event in the slot when free; when the slot is occupied, it appends to _queued_events[session_key]. After each drain, _promote_queued_event() moves the overflow head into the slot. _queue_depth() reports len(overflow) + (1 if slot occupied else 0) — what /queue lists for operators. /new and /reset clear queued human follow-ups; internal wake events pinned for async delegation may survive by design.

busy_input_mode (gateway config) decides what a non-command message does while busy:

  • interrupt (common default) — call interrupt() on the running agent so the new user text becomes steering input; slot pending may be dropped on gateway restart.
  • queue — treat overflow like explicit /queue semantics where configured; survives restart when drain-on-shutdown is enabled.
  • steer — route through running_agent.steer(), including fan-out to active subagents where a blunt interrupt would be unsafe.

Compression locks and active subagents can demote interrupt to queue automatically so you do not orphan a parent-session rotation mid-compaction. Operators feel this as: long task + pasted correction — interrupt pivots the turn; queue mode stacks work; /stop hard-stops regardless of mode.

Delivery: delivery.py and the ledger

Generating a reply is not the same as the user receiving it. Outbound routing lives in gateway/delivery.py (see “Delivery Path” in Gateway internals):

  • Direct reply — send back through the originating platform adapter and chat.
  • Home channel — cron and background results to a configured home channel per platform.
  • Explicit target — addresses like telegram:-1001234567890 for hermes send and cron deliver: targets.
  • Cross-platform — deliver to a different platform than the inbound message (with session context from SessionStore for routing).

Cron deliveries intentionally do not mirror into gateway session history — they stay in cron’s own session to avoid alternation violations.

Around each final platform send, gateway/delivery_ledger.py records a durable obligation in state.db (user-facing semantics in Messaging):

  • record_obligation() — pending before the first send
  • mark_attempting() — immediately before the await
  • mark_delivered() / mark_failed() — only after a definitive SendResult

Semantics are at-least-once. If the gateway dies after the model finishes but before WhatsApp acknowledges, the next boot’s sweep_recoverable() claims rows whose owner process is gone and redelivers stored text instead of re-running the whole turn. A live-process retry sweep handles transient failed rows with backoff (30s / 2m / 10m). Recovery may prefix a duplicate warning when the wire outcome was ambiguous. Ephemeral slash replies and empty bodies skip the ledger; disable with gateway.delivery_ledger: false if you accept crash loss. Active-turn markers coordinate with session recovery: a reply persisted but not ledgered becomes a recoverable row rather than a second full inference.

Circuit breaker

Each platform adapter sits behind a circuit breaker. Repeated retryable failures — disconnects, rate limits, upstream 5xx — trip the breaker: the adapter pauses, logs a structured trip event, and can notify the home channel. Unlike the delivery ledger (which retries obligations), the breaker does not auto-heal; you clear it with /platform resume <platform> once the provider is healthy again. That prevents a sustained outage from reconnect thrash. Use /platform list and gateway logs (circuit breaker, paused) to see what tripped.

Prompt cache and why the Gateway owns the session boundary

Anthropic-style prompt caching attaches cache_control markers to a stable prefix plus the rolling tail of the transcript (agent/prompt_caching.py). The default layout is system-and-3: up to four breakpoints — static system prefix, end of system prompt, and the last three cacheable non-system messages — unless a configured static_system_prefix splits the system block further. Details and hygiene thresholds live in Context compression and caching.

The economic case pairs with the session section above:

  • Reusing the cached AIAgent per session_key keeps breakpoints warm across turns.
  • Cache invalidation is global per agent instance — system prompt, tool schemas, or model route changes force rebuild and cold writes.
  • Multiplexed profiles namespace keys (agent:work:…) so parallel configs do not poison each other’s prefixes.

Gateway session hygiene (rough 85% pre-turn compaction) and in-agent compression (≈50% default) are separate layers, but both assume the Gateway already decided which conversation file to open.

Takeaways

  • Session — build_session_key() names the lane; SessionStore maps it to session_id and SQLite transcripts; run_agent_cache.py LRU-reuses AIAgent instances per key.
  • Auth — ordered allow layers; DM pairing in pairing.py for closed-by-default DMs.
  • Commands — resolve_command() + handler table; busy_policy and inline bypass while a turn runs.
  • Queue — adapter slot + runner busy policy; /queue FIFO via _queued_events with one turn per item.
  • Delivery — delivery.py routes outbound; delivery_ledger.py makes finals at-least-once across crashes.
